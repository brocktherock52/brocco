How to run multiple AI agents in parallel from one prompt

Tab-switching between Claude, ChatGPT, and Cursor for one task is the silent productivity tax of 2026. Here are three patterns for parallel agents that work today, with code you can paste in 5 minutes.

You have a goal. Five steps. Three of them depend on the others, two don't. The right architecture is not "one agent doing everything" or "one tab per step", it's parallel agents that fan out and rejoin. The hard part isn't the model, it's the orchestration. Here's how to do it in three patterns, ranked by how much engineering you'll do.

Pattern 1: Broadcast (one prompt, N agents, no coordination)

The simplest pattern. You have a goal that benefits from multiple perspectives or specializations, and the agents don't need each other's outputs. Send the same prompt to N agents, each with a different system prompt and tool set, in parallel. Wait for all to finish, present results side-by-side.

Use case: "plan my product launch" -> researcher fetches competitor positioning, outreach drafts launch tweets, planner produces a 14-day execution sequence. None of the three needs the others' output.

Implementation in 30 lines using the Anthropic SDK:

import asyncio
from anthropic import AsyncAnthropic

client = AsyncAnthropic()

AGENTS = {
  "researcher": "You research the web. Return a sourced brief.",
  "outreach":   "You draft cold emails and tweets. No AI cliches.",
  "planner":    "You output numbered execution plans, 5-10 verb-first steps.",
}

async def run_agent(name, system, prompt):
    resp = await client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=2048,
        system=system,
        messages=[{"role": "user", "content": prompt}],
    )
    return name, resp.content[0].text

async def broadcast(prompt):
    results = await asyncio.gather(*[
        run_agent(name, system, prompt) for name, system in AGENTS.items()
    ])
    for name, text in results:
        print(f"\n=== {name} ===\n{text}")

asyncio.run(broadcast("plan a launch for a new BYOK AI dashboard"))

That's it. asyncio.gather runs all three agents concurrently. Total wall time = the slowest agent, not the sum.

Tradeoffs: each agent is independent, so they can't reference each other's work. If your goal needs synthesis (combine 3 outputs into 1), this pattern doesn't help, see Pattern 2.

Pattern 2: Supervisor (one agent decomposes, N sub-agents execute, supervisor synthesizes)

The classical multi-agent pattern. One supervisor agent reads the goal, decomposes it into sub-tasks, dispatches each to a specialist via a delegate tool, then synthesizes the results into a final answer.

Use case: "qualify yesterday's signups, draft personalized intro emails to the top 5, post a summary to Slack" -> supervisor reads, decides "step 1 needs the analyst, step 2 needs outreach, step 3 needs slack", calls each, then writes the final summary.

Implementation skeleton:

SUPERVISOR_PROMPT = """You decompose goals and delegate to specialists.
Available specialists (call via the delegate tool):
- analyst: data analysis and pattern-finding
- outreach: cold message drafts
- slack: post messages to Slack

After all delegates return, synthesize a final answer."""

DELEGATE_TOOL = {
    "name": "delegate",
    "description": "Spawn a specialist sub-agent and return its result",
    "input_schema": {
        "type": "object",
        "properties": {
            "agent": {"type": "string"},
            "task": {"type": "string"},
        },
        "required": ["agent", "task"],
    },
}

# Pseudo-code: in the supervisor's tool-use loop, when delegate is called,
# spawn a sub-agent with the named system prompt and the task as user input.
# When the sub-agent finishes, return its final text as the tool result.

Tradeoffs: the supervisor is the bottleneck. If it makes a bad plan, all the work downstream is wasted. Mitigation: keep the supervisor's job small ("decompose and call specialists; do not do the work yourself"). Don't let it write the final synthesis until all sub-agents return.

Pattern 3: Custom fan-out (you write the DAG)

For workflows where some steps depend on others, write the DAG explicitly. This is the "graph runtime" pattern (LangGraph, CrewAI, etc.). You define nodes (agents) and edges (dependencies), then a runtime executes the graph in topological order, parallelizing where possible.

Use case: "research X, then write code based on the research, then write tests for the code, then write docs based on both code and research". Research must finish before coding. Tests can run in parallel with docs (both depend on the same code + research).

You usually don't want to write this from scratch. Use LangGraph if you're a LangChain shop, CrewAI if you want a higher-level abstraction. The graph definition is what you'll iterate on, not the runtime.

How to pick

  • Pattern 1 (Broadcast): independent perspectives, don't need each other. Easiest. 30 lines of code.
  • Pattern 2 (Supervisor): one final answer needed, sub-tasks share no data. Most common in practice. 100-200 lines for a custom impl, or use a library.
  • Pattern 3 (DAG): explicit dependencies between sub-agents. Use a framework, don't roll your own.

The mistake everyone makes

Spawning 5 agents to do work that 1 well-prompted agent could do faster. Parallel agents have an overhead, each one is a separate API call with its own latency. If your task fits in one prompt, use one agent. The math: 5 agents at 8s each running in parallel is still 8s wall-clock, but it's 5x the token cost.

Use parallel agents when the work actually parallelizes. Don't use them as a hammer for tasks that aren't nails.
